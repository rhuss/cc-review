**Goal:** Bring the source-verified cc-review guide from its 2026-11-05 baseline (cc-review v1.4.0, commit `37efe88`) to cc-review v1.9.0 (commit `2c380ea`), updating only the affected pages and diagrams, adding one page for the new GitHub Actions automation, and recording the new baseline last.

**Architecture:** A run of `/guide:evolve`. The controller verifies factual corrections against the target source before they are applied.

**Tech Stack:** GitHub Markdown (gfm) guide, Bash, `uv`, Python toolkit under `tools/guide/`, pandoc build via `make check`, Excalidraw diagrams via the `guide:diagrams` skill.

**Spec:** `docs/guide/spec.md` (the controller updates its `## Why` card and page list for this run before task 1).

- Sections and voices: Overview (`concepts`), Using cc-review (`technical`), How it works (`concepts`), Extending cc-review (`technical`), Reference (`reference`).
- Every page starts with a source block after the title; entries are `<source-id>:<path>[:<lines>]`, `url:<url>`, or (internal pages only) `input:<input-id>`. Facts without a pinned source stay out of the page.
- Inputs are hints, never proof. - Shareable pages never contain confidential terms (none configured) or links into the internal part (`internal/`).
- No em dash or en dash characters in any file.
- gfm format rules: GitHub Markdown; source block and expectations as HTML comments; baseline values as generated regions `<!-- guide:attr <name> -->...<!-- /guide:attr -->` (never inside listings; `make site` rewrites them); admonitions are GitHub alerts (`> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]`, `> [!WARNING]`, `> [!CAUTION]`); cross-references are relative `.md` links; diagrams link to the full-size SVG (`[![alt](assets/diagrams/<name>.svg)](assets/diagrams/<name>.svg)`); pages under `docs/` with the order in `docs/SUMMARY.md`; internal pages under `internal/`.
- Admonitions: only NOTE, TIP, IMPORTANT, WARNING, CAUTION, with their fixed meanings (see `page-procedure.md`).
- Task pages: a why-paragraph, numbered steps with copy-paste commands, `Check:` lines with expectations.
- The start page and the section overview pages follow `overview-contract.md`: why before how, the spec's `## Why` card as their content, every product defined from its own pinned source, and the cold-reader test as their review gate.
- Read every pinned source in the directory printed by `uv run tools/guide/fetch.py where <source-id>`, never in the working tree of a repository. During this run that directory is the target revision.
- Diagrams follow the diagrams skill. Every label, arrow, and frame is a claim with a source in the diagram's claims file (`diagrams/<name>.claims.yaml`); where a product runs its parts comes from its own architecture documentation at the pinned version. Palette: platform gray (`#e9ecef`/`#495057`), governance orange (`#ffe8cc`/`#e8590c`), admin red (`#ffe3e3`/`#c92a2a`), user blue (`#d0ebff`/`#1971c2`); text and legends `#495057`.
- Run every command from the guide project root with path arguments; never `cd` into `.guide/cache/`.
- Containers: `podman`, never `docker`. Python packages: `uv`, never pip.
- Commit messages end with the trailer `Assisted-By: 🤖 Claude Code`. Local commits only; the controller does not push (author's choice for this run).
- Impact set discipline: only the pages and diagrams named in this plan change. Any other page that needs a change is reported, not edited.

## Review Focus

1. **Citations that still point at the old line ranges.** README.md grew and `review.md`, `triage.md`, `issue.md`, `inbox.md` changed length. A citation that resolves but names the wrong lines is Important even when the statement is true.
2. **The renamed plugin reference.** `docs/reviewer-plugins.md` moved to `docs/extras/reviewer-plugins.md`; a page or claims file still citing the old path fails the source check after the rebaseline.
3. **New behavior stated with old semantics.** Review posting is now draft, preview, approve, post; a page that still says a review is posted immediately (or that `--unattended` requires `--bulk`) is wrong.
4. **Unsupported CI claims.** The CI page may only state what `docs/CI.md`, `ci.md`, `unattended.md` and the README state at the target; event names, policy thresholds and provider requirements are exactly what those files say.
5. **The Why card drifts from the start page.** The start page carries the spec's `## Why` card; if the card is not updated for CI, the page either omits a documented capability or contradicts the spec.
