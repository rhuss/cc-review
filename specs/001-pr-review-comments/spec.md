# Feature Specification: PR Review Comments

**Feature Branch**: `001-pr-review-comments`

**Created**: 2026-08-03

**Status**: Draft

**Input**: User description: "Close the feedback loop by posting cc-review findings as inline PR review comments via the GitHub Review Submission API."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Interactive Local Review and PR Posting (Priority: P1)

A reviewer runs `cc-review --pr 42` on a pull request. After the review agents complete and findings are merged and deduplicated, the system presents findings locally for interactive review. Critical and Important findings are shown one at a time with accept, reject, or edit options. Minor and Notable findings are shown in a batch with accept-all, reject-all, or cherry-pick options. After the reviewer finishes accepting or rejecting, all accepted findings are posted as a single GitHub review submission with inline comments at exact file and line locations. The review includes a summary body with what went well, a findings table, source attribution, and the gate outcome.

**Why this priority**: This is the core feature. Without it, cc-review findings remain invisible on the PR, requiring authors to read a local file. Posting to the PR closes the feedback loop and makes cc-review a first-class review participant.

**Independent Test**: Can be tested by running cc-review with `--pr` on any PR with code changes, verifying that accepted findings appear as inline GitHub review comments with the correct structure.

**Acceptance Scenarios**:

1. **Given** a PR with code changes and cc-review produces 3 Critical and 5 Minor findings, **When** the reviewer accepts 2 Critical and 3 Minor findings, **Then** a single GitHub review is posted with 5 inline comments at the correct file/line locations, the review event is `REQUEST_CHANGES`, and the summary body lists all 5 accepted findings with source attribution.
2. **Given** a PR with code changes and cc-review produces only Minor and Notable findings, **When** the reviewer accepts some findings, **Then** the review event is `COMMENT` (not `REQUEST_CHANGES`), and the summary body reflects no critical issues.
3. **Given** a PR with code changes and the reviewer rejects all findings, **When** the interactive review completes, **Then** no GitHub review is posted and the local findings report is still written.
4. **Given** cc-review runs without `--pr`, **When** review completes, **Then** no PR comments are posted; the existing local-only behavior is unchanged.

---

### User Story 2 - Source Attribution Across All Agents (Priority: P1)

A reviewer runs cc-review with `--pr` and findings come from multiple sources: internal agents (correctness, architecture, security, production, test-quality, goal-alignment) and external tools (CodeRabbit, Copilot, Codex). All findings, regardless of source, pass through the same interactive review and posting pipeline. Every posted inline comment includes a source footer identifying which agent or tool produced it, and the summary body lists all participating agents and tools.

**Why this priority**: Without uniform treatment of all finding sources, external tool findings would be second-class citizens. Consistent attribution helps the PR author understand where each finding came from and builds trust in the review process.

**Independent Test**: Can be tested by running cc-review on a PR where both internal agents and at least one external tool produce findings, then verifying all posted comments have correct source footers.

**Acceptance Scenarios**:

1. **Given** a finding was produced by the correctness agent, **When** it is posted as an inline comment, **Then** the footer reads `_Source: correctness agent_`.
2. **Given** a finding was produced by CodeRabbit and also flagged by the security agent (after dedup), **When** it is posted, **Then** the footer reads `_Source: coderabbit (also flagged by: security agent)_`.
3. **Given** findings from 4 internal agents and 2 external tools, **When** the review is posted, **Then** the summary body lists all 6 participating sources.

---

### User Story 3 - Summary with "What Went Well" (Priority: P2)

After the interactive review, the GitHub review submission includes a summary body. Before listing findings, the summary highlights what the PR does well, generated by an agent that analyzes the diff for genuinely good patterns (solid error handling, clean abstractions, good test coverage). The summary also includes a findings table with severity, file, description, and source columns, the count of rejected findings, and the overall gate outcome.

**Why this priority**: Positive feedback matters. A review that only lists problems is demoralizing. Calling out good patterns reinforces them and makes the review feel balanced and constructive.

**Independent Test**: Can be tested by running cc-review on a PR with mixed quality (some good patterns, some issues) and verifying the summary body contains both a highlights section and a findings table.

**Acceptance Scenarios**:

1. **Given** a PR with solid error handling and clear naming, **When** the review is posted, **Then** the summary body contains a "What Went Well" section mentioning specific positive observations.
2. **Given** a PR with 3 accepted findings, **When** the review is posted, **Then** the summary includes a table with columns for Severity, File, Description, and Source.
3. **Given** a review where 2 findings were rejected, **When** the summary is posted, **Then** it states "2 findings reviewed and not posted" without listing rejection details.

---

### User Story 4 - Comment Structure with Reasoning Voice (Priority: P2)

Each posted inline comment follows a structured format: what is wrong, why it matters (severity and impact), and a proposed mitigation. When the prose plugin is installed, comment text is shaped by a dedicated `reviewer` voice profile that is concise, direct, and explains reasoning without being preachy. When the prose plugin is absent, a hardcoded template produces the same structural elements.

**Why this priority**: Clear reasoning prevents dismissive responses like "this is fine." When reviewers explain why something matters and how to fix it, acceptance rates increase and the review becomes a learning opportunity.

**Independent Test**: Can be tested by running cc-review with and without the prose plugin installed, then comparing comment output for structural consistency and tone.

**Acceptance Scenarios**:

1. **Given** the prose plugin is installed with a `reviewer` voice profile, **When** a finding is posted, **Then** the comment text uses the voice profile's tone and includes all three structural elements (what, why, how).
2. **Given** the prose plugin is not installed, **When** a finding is posted, **Then** the comment text uses a hardcoded template with the same three structural elements.
3. **Given** a Critical finding about a null pointer dereference, **When** it is posted, **Then** the comment clearly explains the crash scenario, states severity as Critical, and provides a concrete fix suggestion with code context.

---

### User Story 5 - Re-run Lifecycle Management (Priority: P3)

When cc-review runs with `--pr` on a PR that already has previous cc-review comments (identified by a `<!-- cc-review:run-id:UUID -->` marker in the review body), the system scans previous review threads. Threads where the underlying code fix addresses the finding are resolved. Threads still open receive updated context. New findings not present in the previous run are posted fresh.

**Why this priority**: Without lifecycle management, repeated reviews would accumulate stale threads. Auto-resolving fixed issues and updating open ones keeps the PR clean and the review current.

**Independent Test**: Can be tested by running cc-review twice on the same PR, making a fix between runs, and verifying that the fixed finding's thread is resolved while new findings are posted.

**Acceptance Scenarios**:

1. **Given** a previous cc-review run posted a finding about missing error handling, and the author added error handling in a subsequent commit, **When** cc-review re-runs with `--pr`, **Then** the previous finding's thread is resolved.
2. **Given** a previous cc-review run posted a finding that is still present in the current code, **When** cc-review re-runs, **Then** the thread remains open (not duplicated).
3. **Given** the re-run finds 2 new issues not in the previous review, **When** the review is posted, **Then** only the 2 new findings appear as new inline comments.

---

### User Story 6 - Triage Integration for cc-review Threads (Priority: P3)

The existing `/triage` command is extended to recognize cc-review's own review threads. When someone replies to a cc-review comment (e.g., "fixed in abc123" or "won't fix, this is intentional"), triage assesses the reply against the original finding. If the reply indicates a fix was applied and the code confirms it, triage resolves the thread. If the reply is a reasoned rejection and the assessment agrees, triage resolves the thread. If the reply is unclear or the fix does not address the finding, triage leaves it open.

**Why this priority**: This completes the feedback loop from the PR author's side. Without triage integration, cc-review threads would require manual resolution even after fixes land.

**Independent Test**: Can be tested by posting a cc-review comment, replying with "fixed," and running triage to verify the thread is resolved.

**Acceptance Scenarios**:

1. **Given** a cc-review thread where the author replied "fixed in commit abc123" and the code at that line no longer has the reported issue, **When** triage runs, **Then** the thread is resolved.
2. **Given** a cc-review thread where the author replied "won't fix, this is intentional behavior for backward compatibility," **When** triage runs and assesses the rejection as reasonable, **Then** the thread is resolved with an acknowledgment reply.
3. **Given** a cc-review thread where the author replied "I'll look at this later," **When** triage runs, **Then** the thread remains open.

---

### Edge Cases

- What happens when a finding references a file or line that no longer exists in the PR's head commit? The system skips the inline comment and includes the finding only in the summary body with a note that the location is no longer valid.
- What happens when a finding references a line that exists but is outside the PR diff hunks (unchanged code)? The finding is included in the summary body only, with file/line reference and a note that the location is outside the diff. GitHub's review API only allows inline comments on lines within diff hunks.
- What happens when the PR diff is too large for the GitHub review API's per-review comment limit? The system truncates to the API limit (currently no documented hard cap, but the review limits comments to findings within the diff hunks) and logs a warning about any findings that could not be posted inline.
- What happens when `gh` authentication fails mid-posting? The system writes accepted findings to a local recovery file and reports the authentication failure with instructions to re-run.
- What happens when a finding spans multiple lines? The inline comment is anchored to the `line_start` position, with the full range mentioned in the comment body.
- What happens when the reviewer edits a comment during interactive review? The edited text replaces the original finding description in the posted comment while preserving the source footer and structural elements.

## Clarifications

### Session 2026-08-03

- Q: What happens when a finding references a line that exists in the file but is outside the PR diff hunks (unchanged lines)? → A: The finding is included in the summary body only, with file/line reference and a note that the location is outside the diff. It cannot be posted as an inline comment due to GitHub API constraints.
- Q: What does "resolve" mean for thread lifecycle: post a reply, or use GitHub's thread resolution API? → A: Use GitHub's `resolveReviewThread` GraphQL mutation to collapse the thread, plus a brief reply noting the resolution reason (e.g., "Resolved: fix confirmed in commit abc123").
- Q: What is the scope of the "edit" action in interactive review (FR-022)? → A: Text-only editing of the description and mitigation text. Severity, file, and line are structural properties and are not editable during interactive review.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The review command MUST post findings as inline PR review comments only when `--pr <number>` is explicitly provided.
- **FR-002**: The system MUST present all findings locally for interactive review before posting anything to the PR.
- **FR-003**: Critical and Important findings MUST be presented one at a time with accept, reject, or edit options.
- **FR-004**: Minor and Notable findings MUST be presented in batch with accept-all, reject-all, or cherry-pick options.
- **FR-005**: All accepted findings MUST be posted as a single GitHub review submission using `gh api` to call `POST /repos/{owner}/{repo}/pulls/{pull_number}/reviews`, consistent with the existing `gh`-based patterns in the triage command.
- **FR-006**: The review event type MUST be `REQUEST_CHANGES` when any accepted finding has severity Critical or Important, and `COMMENT` otherwise.
- **FR-007**: Every posted inline comment MUST include: what is wrong, why it matters, and a proposed mitigation.
- **FR-008**: Every posted inline comment MUST include a source footer identifying the originating agent or tool, and any co-reporters after dedup.
- **FR-009**: The review summary body MUST include a "What Went Well" section generated by the goal-alignment agent (which already analyzes the diff against project intent) identifying positive patterns such as solid error handling, clean abstractions, and good test coverage.
- **FR-010**: The review summary body MUST include a findings table with Severity, File, Description, and Source columns.
- **FR-011**: The review summary body MUST list all participating agents and tools.
- **FR-012**: The review summary body MUST include a `<!-- cc-review:run-id:UUID -->` marker for re-run detection.
- **FR-013**: On re-run with `--pr`, the system MUST scan for previous cc-review reviews (identified by the `<!-- cc-review:run-id:UUID -->` marker) and resolve threads where the code fix addresses the finding. Resolution is determined by: (a) extracting the file and line_start from the previous inline comment, (b) checking whether the current review run produced a finding at the same file and overlapping line range, and (c) if no current finding matches, the previous thread is considered resolved. This is location-based matching, not content-based.
- **FR-014**: On re-run, the system MUST post only new findings not present in the previous review. A finding is "present in the previous review" if a previous inline comment exists at the same file and overlapping line range with the same category.
- **FR-015**: All findings MUST be treated uniformly regardless of source (internal agents or external tools like CodeRabbit, Copilot, Codex).
- **FR-016**: The existing local findings report (`review-findings.md`) MUST still be written regardless of PR posting.
- **FR-017**: When the prose plugin is detected at runtime, comment text MUST be shaped by a dedicated `reviewer` voice profile.
- **FR-018**: When the prose plugin is not available, comment text MUST use a hardcoded template with the same structural elements (what, why, how).
- **FR-019**: The triage command MUST be extended to recognize cc-review review threads and assess replies against the original finding.
- **FR-020**: The triage command MUST resolve cc-review threads when a reply indicates a confirmed fix or an acknowledged rejection.
- **FR-021**: When the reviewer rejects all findings during interactive review, no GitHub review MUST be posted.
- **FR-022**: The interactive review MUST support an edit action allowing the reviewer to rewrite the description and mitigation text before posting. Severity, file, and line are not editable.
- **FR-023**: When a finding references a line outside the PR diff hunks, the system MUST include it in the summary body only (not as an inline comment) with a note that the location is outside the diff.
- **FR-024**: When resolving a previously posted cc-review thread, the system MUST use GitHub's `resolveReviewThread` mutation and post a brief reply stating the resolution reason.

### Key Entities

- **Finding**: A review issue with severity, confidence, file location, description, rationale, fix suggestion, and source agent. For PR posting, two transient fields are added during interactive review (not persisted to the finding schema): `accepted` (boolean, whether the reviewer accepted the finding for posting) and `edited_text` (string, optional rewritten description/mitigation text). These fields exist only in the posting pipeline's in-memory state; the finding schema (`finding.schema.json`) is not modified.
- **Review Submission**: A GitHub review containing a body (summary) and a list of inline comments. Created from all accepted findings.
- **Run ID**: A UUID embedded as an HTML comment marker in the review body, linking a review submission to a specific cc-review execution for lifecycle management.
- **Reviewer Voice Profile**: A prose plugin voice configuration defining the tone and style for review comment text. Built into cc-review, not inherited from the project.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Review findings are visible as inline comments on the PR promptly after the reviewer completes interactive review (single API call, no artificial delay).
- **SC-002**: PR authors receive exactly one notification per cc-review run (single review submission).
- **SC-003**: Every posted comment includes all three structural elements (what, why, mitigation) and a source footer.
- **SC-004**: On re-run, previously fixed findings are automatically resolved without manual intervention.
- **SC-005**: Findings from all sources (internal agents and external tools) appear with consistent formatting and attribution.
- **SC-006**: The review summary provides a complete picture: positive observations, findings table, participating agents, and gate outcome.

### Non-Functional Requirements

- **NFR-001**: The PR posting pipeline (from interactive review completion to GitHub API call) MUST make exactly one REST API call for the review submission, keeping API usage predictable.
- **NFR-002**: The re-run scanning phase MUST use paginated GraphQL queries (consistent with triage command patterns) to handle PRs with many existing review threads.
- **NFR-003**: On GitHub API failure during posting, accepted findings MUST be written to a local recovery file (`.cc-review/recovery-<run-id>.json`) so the user can retry without re-running the full review.

### Out of Scope

- GitLab, Bitbucket, or any non-GitHub hosting platform.
- Automatic re-runs triggered by CI events (this feature is CLI-initiated only).
- Modifying the finding schema (`finding.schema.json`); interactive review state is transient.
- Creating or closing PRs; only posting reviews on existing open PRs.

## Assumptions

- The `gh` CLI is installed and authenticated with sufficient permissions to post reviews on the target repository.
- The PR exists and is open when `--pr` is provided. The system does not create PRs.
- GitHub's review submission API supports the number of inline comments cc-review typically produces (up to ~50 per review).
- The prose plugin, if used, is installed as a Claude Code plugin and its voice profiles are accessible at runtime.
- GitLab support is out of scope for this feature; only GitHub via `gh` CLI is supported.
- The `reviewer` voice profile is shipped as part of the cc-review plugin, not generated dynamically.
